# 1. Core Principle

Recommendation يجب أن تكون نتيجة **evidence-based decision**.

لا تستخدم قاعدة بسيطة مثل:

`mastery < X → recommend`

فقط.

يجب أن تجمع عدة إشارات.

---

# 2. Audit First

افحص النظام الحالي بحثًا عن:

* existing recommendation service
* legacy recommendations
* foundation recommendations
* student progress
* curriculum ordering
* lesson ordering
* question recommendations

لا تحذف أي نظام قديم.

إذا كان هناك نظام مناسب، استخدم Adapter أو طبقة جديدة فوقه بدل كسر المسارات الحالية.

# 3. Recommendation Object

أنشئ model/contract واضحًا مثل:

`LearningRecommendation`

يحتوي على الأقل على:

* studentId
* programId
* subjectId
* taxonomyNodeId إن كان معتمدًا
* recommendationType
* priority
* reasonCodes
* evidence
* confidence
* generatedAt
* expiresAt إن كان مناسبًا

لا تسمح للـclient بتحديد recommendation أو priority.

---

# 4. Recommendation Types

ابدأ بعدد محدود:

* `LEARN`
* `PRACTICE`
* `REVIEW`
* `RECOVERY_CHECK`
* `DIAGNOSTIC`
* `MASTERY_CHECK`

لا تضف أنواعًا كثيرة بلا حاجة.

المعنى:

### LEARN

الأدلة تشير إلى أن الطالب يحتاج فهم المادة قبل كثرة التدريب.

### PRACTICE

الفهم موجود لكن يحتاج تطبيقًا.

### REVIEW

هناك معرفة سابقة تحتاج إعادة تنشيط.

### RECOVERY_CHECK

البيانات قديمة أو الثقة انخفضت وتحتاج evidence حديث.

### DIAGNOSTIC

المعلومات غير كافية لاتخاذ قرار موثوق.

### MASTERY_CHECK

الأدلة تشير إلى أن الطالب قريب من الإتقان ويحتاج تحققًا إضافيًا.

---

# 5. Important Separation

لا تخلط:

`Diagnostic`

مع:

`Recommendation`

Diagnostic يقول:

**ما الذي لا نعرفه؟**

Recommendation يقول:

**ما نوع النشاط الذي يمكن أن يقلل هذا uncertainty أو يحسن الأداء؟**

# 7. Decision Logic

أنشئ decision layer واضحة وقابلة للاختبار.

أمثلة فقط لتوضيح الاتجاه:

### No reliable data

إذا:

`diagnosticRequired = true`

يمكن أن تكون recommendation:

`DIAGNOSTIC`

وليس درسًا عشوائيًا.

### Conceptual weakness

إذا توجد أدلة موثوقة ومتكررة على:

`CONCEPT_GAP`

أو:

`MISUNDERSTANDING`

يمكن أن تكون:

`LEARN`

### Understanding but weak application

إذا mastery مناسب لكن توجد أخطاء إجرائية متكررة:

`PRACTICE`

### Previously learned + stale evidence

إذا evidence قديم:

`REVIEW`

أو:

`RECOVERY_CHECK`

حسب data confidence.

### Near mastery

إذا الطالب قريب من mastery لكن confidence غير كافٍ:

`MASTERY_CHECK`

هذه أمثلة، وليست thresholds نهائية.

---

# 8. Do Not Overreact

محاولة واحدة خاطئة لا يجب أن تغير recommendation بالكامل.

مثال:

طالب لديه evidence جيد في موضوع معين ثم أخطأ سؤالًا واحدًا بسبب:

`CALCULATION_ERROR`

لا تحوله مباشرة إلى:

`LEARN`.

نريد stability.

---

# 9. Confidence

كل recommendation يجب أن يكون لها confidence.

افصل:

* recommendation priority
* recommendation confidence

الأولوية لا تعني أن النظام متأكد 100%.

---

# 10. Priority

أنشئ priority قابلة للحساب، لكن لا تستخدم رقمًا عشوائيًا بلا تفسير.

الأولوية يمكن أن تتأثر بـ:

* mastery weakness
* error evidence
* recency
* diagnostic uncertainty
* repeated errors
* importance/coverage إذا كانت هناك بيانات موثوقة

احفظ reason codes التي تفسر سبب ارتفاع الأولوية.

---

# 11. Taxonomy Constraint

حاليًا taxonomy الموثوقة هي:

* Program
* Subject

لا تنشئ recommendation لـ:

* Skill
* SubSkill
* Concept

إلا إذا كانت node معتمدة رسميًا.

لا تخترع prerequisites.

---

# 12. Avoid Duplicate Recommendations

إذا كان نفس recommendation ما زال صالحًا:

لا تنشئ عشرات السجلات المتطابقة.

استخدم deterministic identity أو deduplication strategy.

لكن إذا تغيرت الأدلة بشكل حقيقي، يجب أن يستطيع النظام إنتاج recommendation جديدة.

---

# 13. Recommendation Lifecycle

فكر في:

* active
* completed
* dismissed
* expired

لكن لا تجعل الطالب يرى هذه الحالات في UI الآن إذا لم تكن هناك واجهة.

---

# 14. Recommendation vs Curriculum

لا تعيد ترتيب المنهج كاملًا.

Recommendation Engine يحدد:

**الأولوية الحالية**

ولا يحذف أو يغير curriculum structure.

# 15. APIs

أضف API بسيطة مثل:

`GET /api/learning/recommendations`

اختياريًا:

`?programId=...`

يجب:

* أخذ studentId من session.
* حساب/قراءة recommendations server-side.
* عدم قبول priority أو recommendationType من client.
* حماية student ownership.

---

# 16. Deterministic

إذا كانت مدخلات الطالب نفسها لم تتغير:

يجب أن تكون النتيجة نفسها.

لا تستخدم randomness.

لا تجعل recommendation تختلف في كل request بلا سبب.

1. no data → diagnostic recommendation
2. repeated conceptual evidence → learn
3. procedural errors → practice
4. stale evidence → review/recovery
5. near mastery → mastery check

7. unknown evidence does not create aggressive recommendation
8. recommendation confidence
9. priority calculation
10. reason codes

14. student A cannot access student B recommendations
